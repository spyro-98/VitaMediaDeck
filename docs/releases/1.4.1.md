## Full PAF contract audit and Legacy recovery — 26 October

An earlier console session completed a native frame, then entered Legacy through
an app-generated -0x5049. The [complete contract review](../paf-contract-audit-2026-10-26.md)
compares all 32 PAF boundaries and shared UI integration with six pinned public

same-frame callback assumption; phase gates, timed progress and detailed recovery
reasons cover delayed tasks, idle/suspend and theme switches. Visibility/alpha
errors and boolean ABI types are corrected. Podcast/library/search workers also

14,204 adapter checks, ARM ABI/syntax, UI and persistence/search suites pass before
the next standard build. Actual Sony pixels and the old recovery branch remain
physical acceptance items; the previous log cannot distinguish that branch.

## Native PAF mutex ownership correction — 26 October

The new physical core identifies LW_MUTEX_NOT_OWNED (0x80028186) on
VMDNativePaf: the previous build initialized/mutated PAF on the app thread but
ran it on another. Module/framework/page/widget setup and Run now share one
owner; bounded native tasks consume validated, acknowledged command generations.
Recovery and preference writes stay on the app thread. Initial frame signaling
is checked separately from command processing. The [ownership report](../paf-thread-ownership-2026-10-26.md)
records the exact evidence, previous mock gap, 10,628 ownership-aware adapter
checks and other pre-build validations. Standard identity is unchanged; physical
native rendering remains pending. No emulator/JIT run was attempted.

## Native first-frame correction and extended audit — 26 October

The next console run reaches rendering and traps inside PAF with GXM invalid
value. A [review of public examples and the frame ABI](../paf-frame-audit-2026-10-26.md)
identified an incompatible direct cast: PAF takes a 32-byte frame record, while
CommonDialog supplies 96 bytes with a different order. The adapter now converts
all fields explicitly, validates the target and logs its first descriptor once.
Independent ARM layout probes, 10,434 adapter assertions and the eight-theme
utility/chrome suites passed before creating a new VPK. Standard 1.4.1/01.05 is
retained; real native rendering and media coexistence still need console checks.

## Riproduzione

Revisioni esatte in `release/DEPENDENCIES.lock`. Entrambi i decoder nell'app
collegano il FFmpeg n6.0 modificato per Vita; l'8.1.2 del builder standalone SW
non è la libreria collegata nel VPK. Dopo i builder della toolchain:

```sh
cmake -S . -B build-standard -DCMAKE_BUILD_TYPE=Release \
  -DVITAMEDIADECK_TEST_ID=standard \
  -DVITAMEDIADECK_VIDEO_CLOCK_PROFILE=performance \
  -DVITA_SW_DECODER_PLANAR_UPLOAD=OFF \
  -DVITA_HW_DECODER_CPU_THREADS=3 -DVITA_SW_DECODER_CPU_THREADS=3
cmake --build build-standard -j 4
unzip -t build-standard/VitaMediaDeck.vpk
VITASDK=/path/to/vitasdk bash tools/release-audit.sh \
  --vpk build-standard/VitaMediaDeck.vpk
```

Usare `--allow-dirty` solo durante la preparazione locale prima del commit.
Installare `VitaMediaDeck-1.4.1.vpk` con VitaShell come aggiornamento. La copia
nei Downloads non equivale all'installazione; commit locali e build non equivalgono
a push, tag o pubblicazione di una release GitHub.
